# GIT

이 스킬은 현재 프로젝트의 변경을 검토 가능한 Pull Request와 배포 결과까지 연결한다. 사용자가 "GIT스킬 해줘"라고 요청하면 검증·커밋·푸시·`main` 대상 PR 생성까지 진행하고, 병합을 기다리는 동안 PR의 검증된 변경을 기존 공개 Sites 사이트에 배포한다. PR은 병합하지 않는다. 특정 단계만 요청했다면 그 범위만 수행한다.

1. 프로젝트의 `AGENTS.md`와 관련 명세를 읽고 현재 요청의 범위를 확인한다. 명세가 아직 작성되지 않았거나 구현과 어긋나면 사용자 지시에 맞게 작성·수정한다. 요구사항이 불명확하면 먼저 질문하고 해당 결정에 의존하는 작업을 멈춘다.
2. 작업 시작 시 저장소의 원격 주소, 현재 브랜치·작업 트리, 원격의 최신 `main`을 확인한다. 원격이나 기준 `main`을 확인할 수 없으면 저장소를 추측하지 말고 사용자에게 묻는다. 최신 `main`과 작업 브랜치의 관계를 확인한 뒤 필요한 통합 방법을 정한다. 기존 미커밋 변경이 있으면 변경 목록을 사용자에게 보여주고 이번 작업에 포함할 범위를 결정받는다. 답변 전에는 해당 변경을 스테이징·커밋하거나 덮어쓰지 않는다.
3. 명세와 실제 변경을 대조하고 변경 위험에 맞는 검증을 수행한다. 이 프로젝트의 포트폴리오 작업기록도 실제 작업과 대조해 갱신한다. 이번 요청에 속하는 파일만 선택해 스테이징하고, 변경 내용을 다시 확인한 뒤 커밋한다.
4. 작업 브랜치를 원격에 푸시하고 `main`을 대상으로 Pull Request를 만든다. 제목·본문에는 변경 결과, 검증, 알려진 한계를 적고 생성된 PR을 현재 작업에 연결한다. PR은 검토할 수 있도록 열어 둔다.
5. PR 작업 브랜치의 검증된 변경을 기존 공개 Sites 사이트에 배포한다. 프로젝트의 현행 배포 절차와 사용 가능한 Sites 스킬을 확인해 따른다. 배포 전 기존 Sites 소스와 PR 브랜치를 대조하고, 사이트에만 있는 변경의 처리 범위가 불명확하면 묻는다. 다른 사이트나 공개 범위 변경을 요청했거나 기존 대상이 확인되지 않아도 묻는다. 배포 후 상태와 접근 가능한 실제 화면을 확인하고 버전·소스·검증 결과를 기록한다. 배포 완료를 PR 병합으로 표현하지 않는다.
6. 최종 답변에 커밋, 브랜치, PR, 배포 상태와 확인하지 못한 사항을 구분해 알린다. 실패한 단계가 있으면 완료했다고 쓰지 않는다.

위 기본 흐름은 사용자가 이번 대화에서 확정한 기준이다. 현재 요청이 범위를 다르게 정하면 그 요청을 따르고, 명세나 대상이 여전히 불명확하면 `AGENTS.md`에 따라 질문한다.
